1. Project Overview

1.1 Concept & Value Proposition

Vendora ("Your Campus. Your Community. One Platform.") is a hyper-local, campus-centric digital ecosystem designed to unify fractured university student and faculty interactions into a coherent, high-trust, and sustainable platform.

In traditional campus environments, student commerce and services are fragmented across unverified WhatsApp groups, Discord servers, notice boards, and informal scrap dealers. This leads to rampant scams, price exploitation, untracked waste generation, and lost academic resources. Vendora addresses these challenges by combining:

  1. Verified Academic Identity & Role Governance: A single source of truth for student, faculty, and administrative identities.
  2. Circular Peer-to-Peer Marketplace: Facilitating exchange of second-hand academic textbooks, laboratory equipment, electronics, study furniture, and bicycles.
  3. Campus Circular Economy & Scrap Hub: Facilitating recyclable paper/cardboard/e-waste pickups and zero-cost item giveaways.
  4. Idempotent Financial Settlement Engine: Providing auditable, transparent simulated financial transactions.
  5. Operational Facilities & Administrative Workflows: Student representative verification, staff assignment, and maintenance workflows.

1.2 Core Project Objectives

  • Zero-Trust Perimeter Security: Authenticate every request at the perimeter gateway while keeping internal services loosely coupled and lightweight.
  • Resource Reusability & Affordability: Lower textbook and laboratory kit costs for junior engineering and university students by 50–70% through peer resale.
  • Campus Sustainability: Divert recyclable paper (registers, notebooks, exams) and electronic waste away from general landfills into structured recycling streams.
  • Microservices Isolation: Ensure independent scalability, deployment, and technology flexibility across domain modules while retaining a pragmatic database design for MVP evaluation.

2.2 Security Architecture & Perimeter Header Propagation

Vendora implements a Zero-Trust Perimeter security model:

  1. Client Request: The client sends an HTTP request containing an Authorization: Bearer <JWT> header to the API Gateway (:8080).
  2. Gateway Interception: The Gateway's JwtAuthenticationFilter (executing at Ordered.HIGHEST_PRECEDENCE (-1)) intercepts the call:
    • Verifies if the request matches public routes (e.g., /api/registration/register, /api/auth/login, Actuator, Swagger UI).
    • If protected, extracts the Bearer token and verifies the HMAC-SHA256 signature using the shared secret (VmVuZG9yYUxvY2FsSnd0U2VjcmV0S2V5MzJCeXRlcyE=).
    • Extracts subject (userId), email, and role claims.
  3. Header Sanitization & Injection (Anti-Spoofing):
    • The Gateway explicitly strips any client-provided X-User-Id, X-User-Email, or X-User-Role headers to prevent identity spoofing.
    • It mutates the downstream request by injecting trusted headers directly from verified claims:
      X-User-Id: <id>, X-User-Email: <email>, X-User-Role: <role>.
  4. Downstream Consumption: Microservices (user-service, marketplace-service, scrap-service, payment-service) read the X-User-* headers to enforce role and ownership checks without re-parsing or querying the database for identity verification.

2.3 Inter-Service Communication: Auth ↔ User Service

vendora-auth-service has no direct database connection. When a user logs in:

  1. vendora-auth-service receives LoginRequest(email, password).
  2. It invokes UserServiceClient (Spring Cloud OpenFeign), which makes an HTTP GET request to http://VENDORA-USER-SERVICE/internal/users/auth-details?email=....
  3. The request includes a shared internal secret header: X-Service-Secret: VendoraLocalInternalSecret2026.
  4. InternalAuthController in vendora-user-service validates the secret:
    • If invalid/missing, returns 403 Forbidden.
    • If valid, fetches the user by email, returns AuthUserDetailsResponse containing id, email, passwordHash, role, and accountStatus.
  5. vendora-auth-service compares raw credentials using BCryptPasswordEncoder.matches(), verifies accountStatus == ACTIVE, and issues the signed JWT.

4. Database Design & Entity Relationship Architecture

4.1 Database Architecture: The Consolidated Schema Strategy

Vendora utilizes a Single Consolidated MySQL Database Schema named vendora_db running on port 3306.

Architectural Rationale & Trade-off Analysis

In pure microservices theory, each service owns an isolated physical database (Database-per-Service pattern). For the Vendora MVP, a pragmatic shared-schema with strict logical boundaries was implemented:

  • Operational Simplicity: Eliminates the overhead of configuring, hosting, and migrating 5 separate database servers in a campus development or evaluator environment.
  • Logical Data Independence: Although tables coexist in vendora_db, no microservice shares JPA entity models or repository classes. Cross-service references are stored purely as scalar IDs (sellerId, buyerId, ownerId, userId, listingId).
  • Zero Cross-Service Table Joins: Services access data strictly through REST APIs and Gateway tokens, never via SQL joins across service domains.

6. Pending Implementation & Gaps Analysis

This section provides an honest, granular audit of what is currently incomplete, missing, or requires production hardening within each service:

6.1 vendora-api-gateway

  • Missing Rate Limiting: No Redis or Bucket4j rate-limiting filter is currently active. The gateway does not throttle brute-force login attempts or high-frequency listing queries.
  • Missing Circuit Breakers: Resilience4j is not configured. If a downstream service (e.g., marketplace-service) crashes or encounters thread starvation, the gateway waits for timeout rather than triggering an immediate fallback response.
  • TLS/SSL Termination: Runs on plain HTTP (:8080). Needs HTTPS certificate binding for real-world deployment.

6.2 vendora-auth-service

  • No Refresh Token Flow: JWT tokens are issued with a fixed 1-hour expiration. When a token expires, users must re-authenticate with credentials. A secure refresh-token rotation mechanism (HTTP-only cookies) is not implemented.
  • Stateless Token Invalidation / Blacklisting: When a user logs out, the JWT remains cryptographically valid until its expiration time. A Redis token blacklist or token version counter in vendora_db is needed for immediate revocation.
  • No Password Reset / Forgot Password: There is no endpoint or email delivery mechanism for OTP-based password resets.

6.3 vendora-user-service

  • No Email Verification Workflow: Newly registered users are immediately set to ACTIVE. A campus verification step (sending a verification code to their @campus.edu email) is not implemented.
  • File Upload for Student ID Cards: The RepresentativeApplicationRequest accepts a static string URL (studentIdProofUrl). Multipart file upload directly to cloud storage (e.g., AWS S3 or MinIO) is missing.
  • No Avatar / Profile Picture Upload: Profiles only hold textual metadata.

6.4 vendora-marketplace-service

  • No Physical Binary Image Upload: The ListingRequest expects a pre-hosted image URL string (imageUrl: "https://..."). An image upload endpoint (multipart/form-data) storing to an S3-compatible bucket is pending.
  • No Pagination / Pageable Sorting: GET /api/listings and /api/listings/search return unfiltered List<ListingResponse>. In a large campus catalog with thousands of books, this will cause memory spikes; Spring Data Pageable (page, size, sort) is missing.
  • Order / Payment Linkage: When a seller accepts a request (status = ACCEPTED), the transaction is not automatically linked to the Payment Service. The buyer must initiate payment independently without an atomic order state machine.

6.5 vendora-scrap-service

  • No Dynamic Material Price Table: The system tracks quantity and unit (15.5 KG PAPER), but does not calculate automated monetary payouts based on daily scrap rates (e.g., ₹14/kg for newspaper, ₹10/kg for cardboard).
  • No Automated Payment Payout Trigger: When a scrap request transitions to COMPLETED, it does not automatically generate a payout record in vendora-payment-service to credit the student's UPI ID.

6.6 vendora-payment-service

  • Simulation Only (No Third-Party Gateway Integration): The service validates input and persists payment records, but does not interact with Razorpay, Cashfree, or Stripe webhooks. No real money or sandbox bank transactions are processed.
  • No Escrow / Hold-and-Release Logic: For P2P book buying, funds are immediately marked SUCCESS rather than held in escrow until the buyer inspects the textbook and enters an OTP confirmation.

6.7 vendora-helpdesk-service (:8084)

  • Completely Unimplemented: The service directory does not exist. Ticket entities, repositories, controllers, and staff assignment logic for campus facility repairs remain to be built.

10. Final Evaluation Preparation: Technical Justifications & Viva Questions

This section provides technical defenses and comprehensive answers to questions that academic evaluators, technical mentors, or system architecture examiners are likely to ask regarding Vendora.

10.1 Key Architectural Decisions & Defenses

Q1: "Why did you build Vendora using a Microservices Architecture instead of a Monolithic Spring Boot application?"

Examiner's Concern: Microservices introduce network overhead, eventual consistency issues, and operational complexity. Was it overkill for a campus platform?

Technical Defense:

  1. Independent Lifecycle & Domain Isolation: In an academic institution, different services experience vastly different traffic profiles. The Marketplace and Chat modules experience intense spikes during the start and end of semesters (book exchange periods), while the User Profile and Scrap modules maintain low, steady traffic. Microservices allow the Marketplace service to scale horizontally without duplicating the entire monolithic heap.
  2. Failure Isolation: If the real-time chat or scrap scheduling service encounters an unhandled exception or memory leak, the core authentication and campus security perimeter (Gateway/Auth/User) remain completely unaffected.
  3. Polyglot & Integration Readiness: External integrations (e.g., IoT smart weighing scales for scrap collection or third-party payment gateways) can be modified, tested, and redeployed within their respective microservices without rebuilding or risking the integrity of user identity and academic credentials.
Q2: "You are using a single shared MySQL database (vendora_db). Isn't a shared database considered an anti-pattern in Microservices?"

Examiner's Concern: Microservices should follow the Database-per-Service pattern. Does sharing vendora_db violate service autonomy?

Technical Defense:

  1. Pragmatic Shared Schema for MVP: In an academic evaluation and early staging environment, provisioning, migrating, and monitoring 5 distinct physical database instances causes unnecessary resource consumption on local development machines.
  2. Strict Logical Isolation (Zero Database-Level Coupling): We enforce the core philosophy of Database-per-Service at the application layer:
    • No Cross-Service Repositories: No service injects a repository belonging to another service (e.g., vendora-marketplace-service contains zero references to UserRepository).
    • No SQL Joins Across Service Boundaries: All cross-domain relationships are stored as scalar numeric identifiers (seller_id, buyer_id, listing_id). If the marketplace needs user data, it reads trusted claims passed in HTTP headers or calls the user service via REST.
    • Seamless Migration Path: Because there are no physical foreign key constraints or SQL joins between service tables, decomposing vendora_db into 5 separate physical databases (vendora_user_db, vendora_market_db, etc.) requires only changing connection strings in application.properties without rewriting any business logic or SQL queries.
Q3: "How do you prevent a malicious user from spoofing identity by manually passing X-User-Id: 1 (Admin) in Postman?"

Examiner's Concern: Downstream microservices trust the X-User-Id and X-User-Role headers. Can an attacker simply inject these headers directly?

Technical Defense:

  1. Perimeter Sanitization at the Gateway: The JwtAuthenticationFilter in vendora-api-gateway operates before any request reaches internal routing. It explicitly removes any client-supplied X-User-Id, X-User-Email, and X-User-Role headers before inspecting the JWT token: 
    headers.remove("X-User-Id");
headers.remove("X-User-Email");
headers.remove("X-User-Role");
  2. Cryptographic Claim Extraction: Only after verifying the cryptographic HMAC-SHA256 signature and expiration timestamp does the gateway extract the claims from the tamper-proof JWT payload and inject them into the mutated request stream: 
    headers.set("X-User-Id", String.valueOf(userId));
headers.set("X-User-Email", email);
headers.set("X-User-Role", role);
  3. Internal Network Isolation: In production, downstream microservices run inside a private virtual network (VPC/Docker network) that is inaccessible from the public internet. The only path into the network is through the Gateway, guaranteeing that no request can reach a downstream service without having its headers scrubbed and verified.
Q4: "Why does vendora-auth-service have no database connection? How does it verify credentials?"

Examiner's Concern: Most authentication microservices connect directly to a user database. Why is Auth stateless here?

Technical Defense:

  1. Single Source of Truth for Data Ownership: vendora-user-service is the exclusive owner of the users table and user credential data. Allowing vendora-auth-service to connect directly to the database would create two separate applications modifying or reading the same table, leading to schema coupling.
  2. Feign Client with Internal Security Secret: vendora-auth-service communicates with vendora-user-service via a Spring Cloud OpenFeign client over a dedicated internal endpoint (/internal/users/auth-details). This endpoint is secured using a shared internal secret (X-Service-Secret), ensuring that only internal platform components can request credential hashes.
  3. Stateless Scalability: Because vendora-auth-service holds no database connections, it is extremely lightweight, boots in seconds, and can be scaled horizontally to handle high volumes of concurrent login and token validation requests without exhausting database connection pools.
Q5: "How does your Payment Service prevent duplicate charges if a student clicks 'Pay' multiple times or encounters a network glitch?"

Examiner's Concern: Network retries can cause duplicate payment records in distributed systems.

Technical Defense:

  1. Idempotency Key Mechanism: The client generates a unique UUID Idempotency-Key (transmitted via HTTP header or payload) for each distinct checkout intent.
  2. Pre-Persistence Deduplication: Before creating a new transaction, PaymentService queries the repository by idempotencyKey:
    • If a record with that key already exists, the service skips new transaction creation and immediately returns the previously recorded payment details with an HTTP 200 OK.
    • If the key is new, it persists the transaction with a unique transaction reference and returns HTTP 201 Created.
  3. Unique Database Constraint: The idempotency_key column has a database-level UNIQUE constraint, providing an absolute guarantee against race conditions even under concurrent duplicate HTTP requests.
Q6: "What happens if the Eureka Server crashes? Does the entire platform stop functioning?"

Examiner's Concern: Is the discovery server a single point of failure (SPOF)?

Technical Defense:

  1. Client-Side Cache Resilience: Spring Cloud Netflix Eureka clients (including the API Gateway) cache the service registry locally in memory. If Eureka crashes, the API Gateway continues routing traffic to known instances using its local registry cache until instances change.
  2. Heartbeat & Self-Preservation: Eureka operates in "Self-Preservation Mode." If network jitter occurs, it does not prematurely deregister instances.
  3. High Availability Production Setup: In production, Eureka is deployed in a peer-aware, multi-node clustered configuration across availability zones, ensuring zero downtime if a single node fails.
