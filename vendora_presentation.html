1. Requirement Understanding & Problem Statement

Operational challenges in traditional campuses vs. the Vendora unified solution

Requirements

❌ The Problem in Today's Campuses

  • Unregulated P2P Exchange: Students buy/sell coursebooks, lab supplies, and hostel electronics via informal, fragmented WhatsApp/Telegram groups with scam risks and zero accountability.
  • Hostel Waste Accumulation: Large volumes of recyclable paper registers and usable items are discarded in landfills at semester-end without collection logistics.
  • Manual Maintenance Tracking: Hostel maintenance issues rely on paper logbooks, leading to lost complaints and zero transparency on technician resolution SLAs.
  • Identity & Trust Void: Existing public apps lack university domain verification (@campus.edu) or role governance.

✔️ The Vendora Platform Solution

  • Campus Identity & RBAC: Strict university email binding and 6 role profiles (Student, Faculty, Admin, Maintenance Staff, Collection Staff, Representative).
  • Campus Marketplace: Peer-to-peer resource exchange with categorized search, buyer purchase requests, and seller-ownership security.
  • Scrap & Giveaway Hub: Scheduled doorstep recyclable pickup by staff and free senior-to-junior giveaway claims.
  • Facilities Helpdesk: End-to-end ticketing state machine with category SLA tracking and discussion threads.
  • Simulated Payments: Idempotent transaction persistence with double-charge protection.
Presenter Speech: "Our project addresses the operational fragmentation found in university campuses. Currently, campus commerce happens in unstructured chat groups, hostel maintenance is tracked on paper, and recyclable waste goes into landfills. Vendora solves all four problems within a single platform governed by authenticated university roles."

5. Implementation: User & Authentication Services

Decoupled identity governance, BCrypt encryption, and representative approval

Services

🔐 Vendora Auth Service (:8082)

  • Stateless Architecture: Contains 0 database tables; queries User Service via internal REST.
  • Token Minting: Issues HMAC-SHA256 tokens using JJWT 0.12.6 encoding userId, email, and role with 1-hour expiration.
  • Endpoints: POST /api/auth/login
  • Quality Status: 36 Unit Tests | 96.9% Coverage | Grade A

👤 Vendora User Service (:8081)

  • Campus Profiles: Manages accounts with strict university domain email validation (@campus.edu).
  • Password Security: One-way password hashing via BCryptPasswordEncoder (strength 10).
  • Representative Workflow: Student applies for App Representative → Admin reviews & approves.
  • Endpoints: POST /api/registration/register, GET /api/users/profile, POST /api/users/representative/apply, PATCH /api/users/representative/approve.
  • Quality Status: 51 Unit Tests | 89.7% Coverage | Grade A
Presenter Speech: "The User Service manages campus identity and profile governance, while the Auth Service remains completely stateless. Notice that the Auth Service owns zero database tables; it verifies credentials via an internal REST API. Both services achieve approximately 90% and 97% code coverage respectively."

6. Implementation: Marketplace Service

Campus resource exchange, multi-attribute dynamic search, and buyer-seller chat

Services

📦 Core Domain Entities

  • Listing: Item title, description, category (BOOKS, ELECTRONICS, CYCLES, LAB_EQUIPMENT, FURNITURE), price, condition, status (AVAILABLE, SOLD, INACTIVE).
  • MarketplaceRequest: Buyer purchase offer, requested quantity, negotiation notes, status (PENDING, ACCEPTED, REJECTED).
  • Conversation & Message: Threaded buyer-seller messages for campus meetups.

🛡️ Business Logic & Validations

  • Multi-Criteria Search: Filter listings by category, minPrice, maxPrice, condition, and search keyword.
  • Ownership Guard: Only the original seller (seller_id == X-User-Id) can edit or mark items as SOLD.
  • Input Boundary Checks: Enforces @Positive price, positive quantity, and non-empty titles.
  • Quality Status: 69 Unit Tests | 92.1% Coverage | Grade A

It features multi-attribute dynamic search across categories and price ranges, buyer purchase requests, and threaded chat. 13. Exception Handling & Cross-Cutting Concerns

Standardized JSON error schemas, Aspect-Oriented Logging, and Bean Validation

Cross-Cutting

⚠️ Centralized Exception Handling

Every service implements @RestControllerAdvice with standardized JSON output:

{
  "timestamp": "2026-11-18T09:30:00.123",
  "status": 404,
  "error": "Not Found",
  "message": "Ticket not found with id: 42",
  "path": "/api/helpdesk/tickets/42"
}
  • ResourceNotFoundException → 404 Not Found
  • BadRequestException → 400 Bad Request
  • ForbiddenException → 403 Forbidden
  • ConflictException → 409 Conflict

⏱️ Aspect-Oriented Logging (AOP)

  • Around Advice: Intercepts all Controller and Service methods using @Around pointcuts.
  • Execution Benchmarking: Calculates wall-clock execution time in milliseconds via Spring StopWatch.
  • Zero Stack Trace Leakage: Uncaught exceptions are caught, logged with contextual arguments, and sanitized before returning HTTP 500 to clients.
  • Jakarta Validation: Annotations (@NotBlank, @Email, @Positive) reject invalid inputs at gateway borders.
Presenter Speech: "We handle cross-cutting concerns uniformly across all services. Our GlobalExceptionHandler maps domain errors to standard HTTP status codes without leaking internal stack traces. Meanwhile, Spring AOP Logging intercepts execution across all layers to benchmark performance in real time."
